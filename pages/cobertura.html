02
Metodología

Cómo se midió

Una sola medición consolidada por plataforma, reproducible con dos comandos.

Backend · JaCoCo consolidado

Se ejecutó la regresión completa (./mvnw verify) con el agente de JaCoCo 0.8.14: primero las 363 unitarias y luego las 487 de integración sobre MongoDB en replica set con Testcontainers. Los dos archivos de ejecución se fusionaron con el CLI oficial y se analizaron las 194 clases compiladas: así, una línea solo cuenta como cubierta si alguna prueba —unitaria o de integración— la ejecutó.

Frontend · Vitest sobre código propio

Las 534 pruebas de React/TypeScript corren con el proveedor v8 de cobertura (formato istanbul). La medición incluye únicamente el código propio (landing/ y dashboard/); los módulos generados por JHipster (entities/, modules/, shared/) quedan fuera para que el porcentaje mida lo que el equipo escribe y testea.

Qué mide cada métrica

  • Líneas: código que alguna prueba ejecutó al menos una vez.
  • Ramas: bifurcaciones (if/ternarios) probadas en sus dos caminos — la métrica más exigente.
  • Métodos / funciones: invocados al menos una vez.
  • Sentencias: instrucciones ejecutadas (base del umbral del frontend).

Doble comprobación

La misma suite se ejecutó en IntelliJ con su agente de cobertura como control independiente: 853 total, 853 passed en 41,77 s. Los conteos varían levemente respecto a Maven (contenedores dinámicos de JUnit 5), pero el veredicto coincide: cero fallos.

reproducción · jacoco + vitest
./mvnw -Dskip.npm=true -Dspotless.check.skip=true -Dcheckstyle.skip=true verify java -jar jacococli merge target/jacoco.exec target/jacoco-it.exec --destfile target/jacoco-merged.exec java -jar jacococli report target/jacoco-merged.exec --classfiles target/classes --sourcefiles src/main/java --csv jacoco.csv ./npmw run vitest-run # 534 pruebas + coverage-final.json

06
Cierre

Focos de mejora priorizados

Dónde rinde el próximo esfuerzo de pruebas y qué material no requiere acción.

1 · Ramas backend: 41,3 % → 60 %

Las bifurcaciones son la deuda real. El plan H-05 apunta a casos negativos —validaciones rechazadas, ownership negado, stock insuficiente, montos incoherentes— sobre todo en service/impl y web.rest, donde las líneas ya superan el 86 %.

2 · Panel del cliente sin specs

ProfilePage, AddressesPage, PaymentsPage, InvoicesPage, ShipmentsPage y StoreHome están a 0 %: su lógica se valida hoy por E2E. Un spec por página (render, estados vacíos y errores) cerraría la brecha más visible del frontend.

3 · Material sin acción

Tres zonas bajas son esperables y no se priorizan: los mappers MapStruct generados (38,3 %, código de máquina), las migraciones de seed del catálogo (solo corren en arranque de desarrollo) y el aspecto de logging (0 %: se activa solo con el perfil de debug).

4 · Lo que está sólido

service.impl 91,8 %, web.rest 86,1 %, domain 96,8 % y service.payment 100 %: el núcleo del negocio —checkout, pagos, ownership y facturación— está cubierto por pruebas de integración con transacciones reales sobre MongoDB.
